# ZT-next

A clean-room, self-hosted overlay network protocol in Rust — a modern
alternative to ZeroTier with a commercial-friendly license structure.

## Status

**M0 (crypto) and M1/M2 (handshake + data plane): complete and working end-to-end.**

| Track | Scope | State |
|---|---|---|
| A | ZT-next protocol | M0–M2 done: handshake, packets, sessions, UDP transport |
| B | ZeroTier-compatible shim | Harness ready, not started |

### What works today

```bash
cargo test                            # 115 tests
cargo run -p zt-node --bin demo       # live two-node demo over UDP
```

The demo starts two nodes on the loopback interface, performs a hybrid
post-quantum handshake, exchanges an encrypted frame, and demonstrates that
a replayed datagram is rejected.

See [`docs/protocol.md`](docs/protocol.md) for the wire format.

## Why

ZeroTier's agent is MPL-2.0, but since **August 2025** its controller moved
to a source-available, non-commercial-only license. Self-hosting ZeroTier
commercially now requires a license negotiation with ZeroTier, Inc.

ZT-next is an independent implementation with:

- **Short-lived, key-bound credentials** instead of long-lived bearer
  capabilities — a stolen credential alone cannot be used to join a network.
- **Per-network addressing** — a node has a different address on each
  network, which makes per-network ACLs trivial and removes cross-network
  address collisions.
- **Only standardized cryptography** — ChaCha20-Poly1305, X25519, HKDF-SHA256,
  standard Ed25519. No hand-rolled ciphers, hashes, or KDFs.
- **Per-network relays** instead of global root/planet hierarchy, so
  self-hosting does not depend on any central infrastructure.
- **Full source ownership of the control plane.**

## Design

### Cryptography

| Purpose | Primitive | Standard |
|---|---|---|
| Symmetric encryption | ChaCha20-Poly1305 | RFC 8439 |
| Key agreement | X25519 | RFC 7748 |
| Key derivation | HKDF-SHA256 | RFC 5869 |
| Signatures | Ed25519 | RFC 8032 |
| Addressing | SHA-256 | FIPS 180-4 |
| **Post-quantum KEM** | **ML-KEM-768** | **FIPS 203** |
| **Post-quantum signatures** | **ML-DSA-65** | **FIPS 204** |

No bespoke cryptography anywhere in `zt-crypto`.

### Post-quantum resistance

The default is **hybrid**: a classical primitive combined with a NIST-standard
post-quantum primitive, secure as long as *either* holds. This follows the
same construction used by Chrome and Cloudflare for TLS.

| Purpose | Classical | Post-quantum | Combined |
|---|---|---|---|
| Key agreement | X25519 | ML-KEM-768 | 64 B shared secret |
| Signatures | Ed25519 | ML-DSA-65 | 3373 B |

Suites are negotiated before the handshake, preferring hybrid, then pure PQ,
then classical. The negotiated suite is bound into the authenticated
transcript so a downgrade is detected.

**The PQ cost is per-session, not per-packet.** A hybrid handshake is
~2.3 KB; the data path afterwards is unchanged, so throughput is unaffected.

See [`docs/post-quantum-design.md`](docs/post-quantum-design.md) for the full
rationale, size tables, and design trade-offs.

### Addressing

```
network_address = SHA256("zt-next/addr/v1" ‖ network_id ‖ ed25519_pubkey)[0..10]
```

Deterministic, no rejection loop, and different per network.

### Credentials

```
┌────────┬──────────┬────────────┬──────────┬────────────┬──────────┐
│ version│ network  │ node_addr  │ issued_at│ not_after  │ ttl_secs │
│ u8     │ id u64   │ [u8;10]    │ u64      │ u64        │ u32      │
├────────┴──────────┴────────────┴──────────┴──────────┴──────────┤
│ public_key [u8;32]  │ controller_id [u8;16] │ nonce [u8;16]        │
├─────────────────────┴────────────────────────┴────────────────────┤
│ signature (Ed25519 ‖ ML-DSA-65)                                 │
└───────────────────────────────────────────────────────────────────┘
```

A 24-hour default TTL means a compromised credential stops working on its
own. Revocation is achieved by refusing renewal, bounded by one TTL, with no
push list required.

## Regenerating golden vectors

```bash
cargo run -p zt-testvectors --bin gen_vectors -- next
```

The committed vectors are checked by `crates/zt-testvectors/tests/golden_vectors.rs`.
Any change to crypto output breaks that test — it is the guard against
accidental wire-format changes.

## Track B: ZeroTier compatibility

The legacy shim will let ZT-next nodes participate in existing ZeroTier
networks. The verification harness is already in place:

```bash
# Build the oracle against ZeroTier's MPL-2.0 sources
./scripts/build-oracle.sh ~/compose/zerotierone

# Emit reference vectors from ZeroTier's own implementation
./target/oracle/zt-oracle vectors/legacy
```

The oracle calls ZeroTier's `node/` API directly and emits vectors in the same
JSON format as the Rust side, so the two can be diffed directly.

See [`docs/legacy-protocol-facts.md`](docs/legacy-protocol-facts.md) for the
verified wire-format details.

## UI console

A production-oriented operations console for ZT-next lives in [`apps/console`](apps/console).
It renders live controller state across network, node, policy, relay, and activity views,
with Apple HIG styling, light and dark themes, and explicit loading, error, empty, and
stale states.

```bash
# Terminal 1 — start the control plane
cargo run -p zt-controller --bin zt-controller

# Terminal 2 — start the console
cd apps/console
npm install
npm run dev
```

The console proxies `/api` to the local controller automatically. Set
`VITE_ZT_USE_FIXTURES=1` to run against bundled demo data instead.

## Controller

The control plane is implemented in `crates/zt-controller` and exposes a JSON API
under `/api/v1`. It supports a hybrid tenancy model: small tenants share one
controller with strict row-level isolation, while larger tenants get dedicated
controllers. A master console API administers tenant lifecycle, plans, limits,
and control-plane health. See [`docs/multi-tenancy.md`](docs/multi-tenancy.md).

```bash
cargo run -p zt-controller --bin zt-controller
```

It manages networks, node enrollment, short-lived credential issuance and
renewal, default-deny access policies, per-network relays, and an append-only
audit log. State is persisted in SQLite; the controller signing key is stored
separately with owner-only permissions. See
[`docs/controller-api.md`](docs/controller-api.md).

## Interoperability

ZT-next can speak its native protocol, the Tailscale/WireGuard dialect, and
the legacy ZeroTier dialect over the same UDP transport. The dispatcher lives
in `crates/zt-node/src/dialect.rs` and the dialect implementations in
`crates/zt-legacy`.

The ZeroTier dialect is verified against golden vectors generated by
ZeroTier's own C++ implementation. See
[`docs/interoperability.md`](docs/interoperability.md) for the architecture,
the remaining work, and the honest trade-offs.

## Licence

Two licences, split along the crate boundary.

| Part | Licence |
|---|---|
| `crates/zt-crypto`, `crates/zt-testvectors` | **MPL-2.0** ([LICENSE](LICENSE)) |
| Everything else — controller, agent, node, TUN, legacy dialects, console | **AGPL-3.0 or commercial** ([LICENSE-CONTROLLER-NOTICE.md](LICENSE-CONTROLLER-NOTICE.md), [LICENSE-CONTROLLER](LICENSE-CONTROLLER)) |

The core is the part meant to be reused: another implementation of the
protocol, in any language, may build on it under the MPL's file-level
copyleft, which asks only that changes to the MPL files themselves be
published.

The controller and the orchestration are the network-facing half, and they
are dual-licensed the way ZeroTier itself moved: **AGPL-3.0**, or a
commercial licence. Self-hosting under the AGPL is free and needs no
negotiation. The commercial licence is for deployments that would rather
not have the AGPL's copyleft obligation reach the code they expose over a
network.
